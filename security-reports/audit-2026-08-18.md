# تقرير الفحص الأمني الشامل — مشروع ERP
**تاريخ الفحص:** 2026-08-18
**نطاق الفحص:** Backend (NestJS/TypeORM) + Frontend (React/TypeScript) — فحص استقصائي بدون تعديل أي كود.

> **ملاحظة منهجية مهمة:** هذا الفحص يغطي الكود المصدري فقط (Authorization/IDOR/Injection/Mass-Assignment/Secrets/XSS/CSRF). لا يغطي جوانب البنية التحتية (تشديد إعدادات السيرفر، جدار الحماية، شهادات SSL الفعلية، صلاحيات نظام التشغيل على VPS) لأنه لا يوجد وصول لسيرفر الإنتاج. "آمن بنسبة 100%" غير قابل للتحقق من الكود وحده — هذا التقرير يقدّم أعلى درجة ثقة ممكنة على مستوى الكود.

## ملخص تنفيذي

| الخطورة | العدد | قابلة للاستغلال فعلياً الآن؟ |
|---|---|---|
| 🔴 Critical | 6 | **نعم — 5 من أصل 6** |
| 🟠 High | 8 | 3 قابلة للاستغلال، 5 تتطلب صلاحية Admin فقط اليوم |
| 🟡 Medium | 5 | جزئياً |
| ⚪ Low / معلوماتي | 6 | لا (أو غير مستغَلة حالياً) |

**أخطر 3 نقاط تستحق إصلاحاً فورياً:**
1. أي مستخدم بدور "Manager" (وليس فقط Admin) يقدر يحذف شركة أخرى كاملة (مع كل فروعها وربطها بالمستخدمين) عبر استدعاء API واحد.
2. وحدات كاملة (المشتريات، الخزينة/الكاش بوكس، مراكز التكلفة) بلا أي عزل بين الشركات إطلاقاً — أي مستخدم عنده صلاحية الوحدة يقدر يقرأ/يعدّل/يحذف بيانات شركة تانية.
3. شاشة إنشاء فاتورة المبيعات بتسرّب تكلفة الشراء وهامش الربح لدور "مندوب" المفروض ميشوفهاش أصلاً — البيانات دي فعلياً موجودة في استجابة الـ API ومعروضة على الشاشة.

## 🔴 Critical — قابلة للاستغلال حالياً

### C-1. `settings/companies.controller.ts` — بلا أي عزل بين الشركات
**الملف:** `backend/src/modules/settings/companies.controller.ts:22-39`
`CompaniesService` يمتد من `BaseCrudService` غير المُعزول. دور "Manager" المزروع في الـ seed (`run-seed.ts:393-396`) عنده صلاحيات `settings.company.view/create/edit/delete` بدون `allCompanies` وبدون `restrictedCompanyId`.

**الاستغلال:** مستخدم Manager في شركة AC يقدر:
```
GET /api/settings/companies              → يشوف كل الشركات التلاتة
PATCH /api/settings/companies/{STAT-id}  → يعدّل بيانات شركة القرطاسية
DELETE /api/settings/companies/{STAT-id} → يحذف شركة القرطاسية بالكامل
```
والحذف بيعمل **CASCADE** على `Branch` و`UserCompany` (`branch.entity.ts:56`)، يعني بيمسح فروع الشركة التانية وربطها بالمستخدمين معاها.

**الإصلاح المطلوب:** تحويل `CompaniesController`/`CompaniesService` لاستخدام نمط العزل الصحيح المُستخدم في باقي شاشات Settings (`CompanyScopedCrudService`)، أو تقييد هذه العمليات على `allCompanies` (Administrator) فقط — الأخيرة أنسب لأن إدارة كيانات الشركات نفسها منطقياً عمل إداري مركزي.

### C-2. Mass Assignment كامل عبر `Partial<Entity>` — 17 نقطة نهاية في 4 وحدات
**السبب الجذري:** `ValidationPipe` (مُفعّل بشكل صحيح في `main.ts:23-28` بـ `whitelist: true`) **لا يعمل إطلاقاً** لو الـ `@Body()` معرّف بنوع `Partial<EntityClass>` بدل DTO class حقيقي — لأن NestJS بيشوف الـ metatype `Object` ويتخطى الفحص كليةً (تم التحقق فعلياً بتجربة `ts-node` على المشروع نفسه).

**الملفات المتأثرة:**
- `backend/src/modules/accounting/cost-centers/cost-centers.controller.ts:38,43,60,65,82,87`
- `backend/src/modules/purchasing/purchasing.controller.ts:55,70,75,94,106`
- `backend/src/modules/treasury/treasury.controller.ts:32,37,53,58`
- `backend/src/modules/parties/sales-representatives.controller.ts:1100,1108`

**الاستغلال (مثال الأخطر):**
```
PATCH /api/treasury/cash-boxes/{id}
Body: { "currentBalance": 999999999 }
```
مستخدم عنده صلاحية `treasury.cash-box.edit` (المفروض بس يعدّل اسم/عملة الخزينة) يقدر يكتب أي رقم في `currentBalance` مباشرة، متجاوزاً كل حسابات الرصيد المبنية على حركات الخزينة الفعلية. نفس المبدأ في `purchasing` (تعديل `status`/`grandTotal` لأمر شراء) وفي `sales-representatives` (تعديل `commissionRate`/`userId` مباشرة).
**كمان:** إرسال `id` بيخص صف موجود بالفعل في عملية *إنشاء* يخلي TypeORM يعمل upsert فوق الصف الموجود (حتى لو بتاع شركة تانية) بدل إنشاء صف جديد.

**الإصلاح المطلوب:** استبدال كل `Partial<Entity>` بـ DTO class حقيقي (`CreateXDto`/`UpdateXDto`) بحقول محددة و`class-validator` decorators — نفس النمط الصحيح المستخدم في كل باقي المشروع.

### C-3/C-4. وحدتا المشتريات (Purchasing) والخزينة (Treasury cash-boxes/bank-accounts) — بلا عمود `companyId` إطلاقاً
**الملفات:** `backend/src/modules/purchasing/entities/purchasing.entity.ts`، `backend/src/modules/treasury/entities/treasury.entity.ts`
الكيانات دي (`PurchaseOrder`, `PurchaseInvoice`, `PurchasePayment`, `CashBox`, `BankAccount`) معندهاش عمود `companyId` من الأساس — الكود فيه تعليق صريح إنها "scaffold" (بنية أولية) لسه محتاجة استكمال.

**الاستغلال:** أي مستخدم عنده صلاحية `purchasing.order.*` أو `treasury.cash-box.*` من *أي شركة* يقدر يقرأ/يعدّل/يحذف أوامر شراء وفواتير ومدفوعات وخزائن شركة تانية بالكامل — دي مستندات مالية حقيقية، مش بيانات إعدادات.

**الإصلاح المطلوب:** إضافة عمود `companyId` للكيانات دي، وتحويل الخدمات لاستخدام نمط العزل القياسي (`findOneScoped`)، بالإضافة لإصلاح C-2 في نفس الوحدات.

### C-5. `SalesLineEditor.tsx` — تسريب تكلفة الشراء وهامش الربح لدور "مندوب"
**الملف:** `frontend/src/features/sales/SalesLineEditor.tsx`
شاشة إنشاء فاتورة المبيعات (اللي دور "مندوب" بيوصلها عادي بصلاحية `sales.invoice.create`) بتجيب المنتجات من `GET /inventory/products` الكامل (يشمل `purchasePrice`) بدل نقطة النهاية المُقيَّدة `rep-view` اللي المشروع نفسه عملها من قبل بالظبط لمنع الموضوع ده في شاشة المنتجات (`ProductsService.findRepViewForCompany`).
والأخطر: البيانات دي **معروضة فعلياً على الشاشة** بدون أي فحص `hasPermission`/`isSalesRep` — `suggestedPrice`, `profit`, تحذير "أقل من التكلفة" (أسطر 281-304, 403-425, 519-536).

**الإصلاح المطلوب:** تعديل `SalesLineEditor.tsx` ليستخدم نقطة نهاية مقيدة الحقول عند `isSalesRep === true` (على غرار `rep-view`)، مع إخفاء/عدم إرسال حقول `purchasePrice`/`profit`/`suggestedPrice` بالكامل من الـ API نفسه لهذا الدور — وليس فقط إخفاءها بصرياً.

### C-6. كلمات مرور مُبَيَّتة بالكامل بدون أي بديل عبر متغيرات البيئة
**الملفات:**
- `backend/src/database/seeds/run-seed.ts:819-820` — حساب مدير إضافي بكلمة مرور ثابتة `makroom204` بدون أي `process.env` بديل، ومُسجَّل كذلك بريده الإلكتروني الحقيقي في الكود.
- `backend/src/database/seeds/demo-data-seed.ts:359` — كلمة مرور مدير تجريبي ثابتة `Manager@123` بدون بديل.

هذان السكربتان يعملان **تلقائياً مع كل تشغيل للحاوية** (`docker-compose.yml:44`: `command: sh -c "npm run schema:sync && npm run seed && node dist/main.js"`)، وكمان بيطبعا كلمة المرور بنص صريح في الـ logs (`run-seed.ts:834`, `demo-data-seed.ts:366`).

**الإصلاح المطلوب:** تحويل الكلمتين لمتغيرات بيئة إجبارية بدون قيمة افتراضية (يفشل التشغيل لو المتغير مش موجود بدل ما يستخدم قيمة ثابتة معروفة للجميع)، وحذف أي `console.log` لكلمة مرور صريحة.

## الخطوات التالية المقترحة

نظراً لحجم النتائج وكون النظام يخدم بيانات مالية حقيقية لعملاء فعليين، أقترح ترتيب الإصلاح كالتالي بدل تعديل كل شيء دفعة واحدة:

1. **إصلاح فوري (Critical، تأثير كبير وتغيير كود محدود):** C-1 (شركات)، C-6 (كلمات المرور المُبيَّتة)، C-5 (تسريب تكلفة المنتج لـ مندوب).
2. **إصلاح عاجل (Critical، تغيير أوسع):** C-2/C-3/C-4 معاً — تتطلب إعادة كتابة الـ DTOs وإضافة عمود `companyId` لثلاث وحدات (Purchasing/Treasury/Cost-Centers) وتعديل الخدمات المرتبطة.
3. **إصلاح High** حسب الأولوية أعلاه.
4. Medium/Low — حسب الوقت المتاح، أثرها الحالي محدود.

قولّي أبدأ بإصلاح أي مجموعة، وهقدملك الكود المُعدَّل جاهز للمراجعة قبل ما ننشره، مع فحص TypeScript الكامل والتحقق المباشر في المتصفح قبل التأكيد.
